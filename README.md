# WinBox Comment Patcher

Нативное macOS-приложение на Swift / AppKit, добавляющее отображение комментариев
Windows-1251 в MikroTik WinBox наряду с UTF-8.

Патчер изменяет **выбранное существующее приложение по прежнему пути**.
Отдельный пропатченный WinBox создавать или выбирать папку сохранения не нужно.
Перед изменением сохраняется резервный ZIP исходного приложения. При ошибке
после замены выполняется откат.

## Для чего нужен патч

WinBox декодирует байты комментариев как UTF-8. Старые комментарии, записанные
в Windows-1251, могут отображаться с неправильными символами или `�`.
Патч добавляет декодирование исходных байтов до создания строки интерфейса.

Доступны три режима:

| Режим | Поведение |
| --- | --- |
| Автоматически | Корректный UTF-8 сохраняется; иначе вся строка декодируется как Windows-1251. По умолчанию. |
| Всегда Windows-1251 | Принудительное декодирование старых комментариев в Windows-1251. |
| Только UTF-8 | Строгий UTF-8 без переключения кодировки. |

Полностью надёжное автоопределение невозможно: байты `D0 A1` означают `С`
в UTF-8 и `РЎ` в Windows-1251. Для таких случаев предусмотрен принудительный режим.

## Требования для работы

| Требование | Значение |
| --- | --- |
| ОС | macOS 12 или новее |
| Процессор | Apple Silicon или Intel; патчер и встроенная библиотека universal |
| Целевое приложение | Исходная universal-сборка **WinBox 4.4.102000** |
| Доступ | Чтение приложения и запись в его родительскую папку |
| Состояние WinBox | Выбранное приложение должно быть закрыто |
| Диск | Поддержка атомарного обмена каталогов; место для временной подготовки и резервного архива |

Проверяется SHA-256 файла `Contents/MacOS/WinBox`:

```text
e68085d6af5d3b54227c522cb2b9416e132779fa70ad9433771cc54f181c35ae
```

Другая сборка, другой исполняемый файл или уже применённый патч отклоняются.
Совпадения одного номера версии недостаточно. Python, Xcode и интернет
при работе готового приложения не нужны.

Патчер и изменённый WinBox получают локальную подпись **ad-hoc**.
Developer ID и Apple notarization в текущую сборку не включены;
корпоративные политики macOS могут ограничивать запуск таких приложений.

## Использование

1. Скачайте `WinBox-Comment-Patcher-<версия>.zip` из раздела **Releases** и распакуйте.
2. Закройте выбранный WinBox.
3. Откройте **WinBox Comment Patcher.app**.
4. Нажмите **«Выбрать WinBox…»** и выберите установленное приложение.
5. Выберите режим кодировки и нажмите **«Применить патч»**.
6. После сообщения **«Готово»** запускайте WinBox по прежнему пути.

Повторное применение к уже изменённому бинарному файлу не выполняется.
Чтобы вернуться к исходному WinBox, используйте резервный архив или исходную
дистрибуцию той же сборки.

## Резервное сохранение и восстановление

Резервные архивы и JSON-журналы находятся в скрытой папке
`.winbox-comment-backups` рядом с выбранным приложением. Папку можно открыть
в Finder через **«Переход → Переход к папке…»**.

Подготовка и строгая проверка подписи выполняются во временной папке.
Проверенное обновление переносится во временную область рядом с выбранным
WinBox, затем каталоги атомарно меняются местами. Это сохраняет обмен
внутри одной области File Provider, в том числе для папок iCloud.
После замены проверяются хеш бинарного файла и полная подпись приложения.

| Состояние журнала | Значение |
| --- | --- |
| `prepared` | Резервный архив готов; операция могла прерваться около момента замены. Сверьте текущий хеш с `original_sha256` и `patched_sha256`. |
| `committed` | Патч применён и проверен. |
| `rolled_back` | После ошибки восстановлено исходное приложение. |
| `rollback_failed` | Сохранены резервный архив и временный оригинал по пути `recovery_application`; сообщение об ошибке содержит оба пути. |

Для ручного восстановления закройте WinBox, распакуйте резервный ZIP
во временную папку и замените приложение восстановленным оригиналом.

## Область изменения и ограничения

- Перенаправляется декодирование роли комментария `CommentRole (0x104)`
  в `BaseTableModel::data` для arm64 и x86_64. Эту роль читают таблица
  и `WTableModel::getComment`.
- Общий UTF-8-декодер Qt и функции отправки конфигурации не изменяются.
  При чтении сохраняются исходные байты модели.
- Отдельные пути `SComment / TextView` в окне объекта не патчатся.
- Редактирование и запись комментариев остаются штатными операциями WinBox.
  Проверка сохранения комментариев на реальном RouterOS не выполнялась.
- Неопределённый байт Windows-1251 `0x98`, неверный ввод в строгом режиме
  или строка длиннее 1 МиБ приводят к пустому отображению.

Репозиторий содержит исходники патчера и профиль адресов. Сам WinBox,
его пропатченные экземпляры, резервные архивы и пользовательские данные
в репозиторий и релизы не включаются.

## Сборка из исходников

Нужны macOS, Xcode с выбранным macOS SDK, Python 3.10+ и стандартные инструменты
`xcrun`, `swiftc`, `clang`, `lipo`, `codesign`, `ditto`.
Сторонние Python-пакеты не требуются.

```bash
make build
make test
make verify
```

Эквивалент без Make:

```bash
python3 build.py
python3 tests/test_codec.py
python3 tests/test_bridge.py
python3 SwiftPatcher/build.py
python3 scripts/verify_package.py
```

Результаты находятся в `SwiftPatcher/dist/`:

- `WinBox Comment Patcher.app` — универсальное GUI-приложение;
- `WinBox-Comment-Patcher-<версия>.zip` — готовый архив;
- `SHA256SUMS` — контрольные суммы архива и метаданных;
- `build-info.json` — версия, архитектуры и поддерживаемый профиль WinBox.

Версия патчера задаётся только в файле [`VERSION`](VERSION).
Версия поддерживаемого WinBox и адреса переходов задаются в [`profile.json`](profile.json).
Обновление этого профиля требует отдельного анализа новой сборки WinBox.

## Тесты

Обычные тесты не требуют установленного WinBox: проверяются все байты
Windows-1251, более 20 000 последовательностей по независимым декодерам Python,
режимы моста, конфигурация и диагностические счётчики. Проверка ZIP распаковывает
именно релизный архив и проверяет подписи, обе архитектуры и встроенный профиль.

Дополнительные интеграционные проверки требуют исходного совместимого WinBox:

```bash
python3 SwiftPatcher/test_in_place.py --source /Applications/WinBox.app
```

Тест создаёт собственные временные экземпляры настоящего приложения,
проверяет изменение на месте, содержимое резервных ZIP, отказ при повторном
применении и откат при принудительной ошибке после замены.
Установленный исходный WinBox этим тестом не изменяется.

Для проверки декодирования в уже пропатченном тестовом WinBox:

```bash
python3 tests/run_native.py --app /path/to/patched/WinBox.app
python3 tests/run_native.py --arch x86_64 --app /path/to/patched/WinBox.app
```

Здесь вызывается реальный обработчик `BaseTableModel::data` с короткими и длинными
строками; тестовый процесс завершается до `WinBox main` и подключения к роутеру.
Для запуска x86_64 на Apple Silicon нужна установленная Rosetta.
Эти интеграционные проверки **не запускаются на GitHub-hosted runner**:
совместимая проприетарная сборка WinBox в CI не загружается.

## GitHub Actions и Release

Workflow [Build and Release](.github/workflows/build-and-release.yml):

1. При push в `main`, pull request и ручном запуске выполняет тесты,
   собирает arm64 + x86_64, подписывает приложение и проверяет ZIP.
2. Сохраняет ZIP, `SHA256SUMS` и `build-info.json` как Actions artifact.
3. При push тега `v<версия>` после успешной сборки создаёт GitHub Release
   и прикладывает те же проверенные файлы. Повторный запуск обновляет вложения.

Используется runner `macos-15`; версия тега обязана совпадать с `VERSION`.
Обычные сборки имеют только `contents: read`. Право `contents: write` задано
только задаче публикации. Для публикации используется встроенный `GITHUB_TOKEN`;
PAT и Apple-сертификаты не нужны. GitHub Actions должен быть разрешён в репозитории.
См. [документацию GitHub о токене](https://docs.github.com/en/actions/tutorials/authenticate-with-github_token)
и [создании релиза](https://cli.github.com/manual/gh_release_create).

Первый релиз после самостоятельной публикации репозитория:

```bash
git push -u origin main
git tag -a v1.1.0 -m "WinBox Comment Patcher 1.1.0"
git push origin v1.1.0
```

Для следующего релиза измените `VERSION`, закоммитьте изменение и отправьте
соответствующий тег. Например, `VERSION=1.1.1` требует тега `v1.1.1`.
Ручной запуск workflow создаёт artifact, но сам по себе не публикует Release.

Проверка скачанных файлов:

```bash
shasum -a 256 -c SHA256SUMS
```
